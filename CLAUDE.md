# Octapu System: notes for Claude

A markdown-based project management system (PMS). It holds several **entities** (separate organisations, each a folder listed in `entities.csv` in the main folder), each made of **tentacles** (its orgs and sub-orgs, rows of `_Options/Tentacles.csv`). A project's person in charge is its **leader** (`_Options/Leaders.csv`). Data are plain markdown and CSV files that the user also edits by hand (e.g. in Obsidian) and shares between machines with Syncthing. `_Dashboard/` is a local web app that reads and edits those files.

The README is the user-facing reference. Its sections on file layout, code organisation, options and markdown formats are accurate, so read the relevant section before changing behaviour. `_Help_Guide.md` is the step-by-step guide shown in the app.

## Running
- `node _Dashboard/server.js` → http://127.0.0.1:4173 (`PMS_PORT`, `PMS_HOST` env vars). No `npm install`; there is no package.json.
- Unit tests: `node --test` from `_Dashboard` (`test/*.test.js`, `node:test`, pure functions plus `writeFileSafely`'s retry). Also verify by running the server on a scratch copy and exercising the page or API (curl the `/api/*` routes; POSTs need `Content-Type: application/json` and a matching `Origin`).
- `dev/api-snapshot.js <port> record|compare <file>` records every GET answer for each entity and diffs them later: record before a refactor, compare after. `dev/sweep.js <port> [shots-dir]` loads every page of every entity in headless Chrome (`dev/cdp.js`, `CHROME_PATH`) and reports script errors. The port is required, so it can't hit a stale server.
- The repo *is* the user's live data. Test against a copy (e.g. `tar` the folder, minus `.git`, into the scratchpad and run there on another `PMS_PORT`), so edits, change logs and conflict files don't land in real files. Pick the entity for a curl with `-b "pms_entity=Label"`.
- Developed on Windows (Git Bash + PowerShell). Python isn't assumed; use node for scripts.

## Hard rules / conventions
- **Zero dependencies.** Node built-ins only on the server, plain browser JS (IIFE per file, `'use strict'`) on the client. No build step, no frameworks, no CDN.
- **Data folders vs app**: each entity's folder (`Label/`, `Freelance/`, from `entities.csv`) holds `_Tentacles/`, `Projects/` (and any other dir named in its `PROJECTS`, relative to the entity folder), `_Networking/`, `_Time_Management/`, `_Catalogs/`, `_Options/`, `_Incubator.md`, `_Archive.md`. `_Images/`, `_Help_Guide.md` and `entities.csv` stay shared in the main folder. All of these are user data. `_Dashboard/` is the app. `_Dashboard/defaults/` holds the shipped Help Guide, screenshots, logo and colours, which are copied in only if missing.
- **Help Guide is duplicated**: `_Help_Guide.md` (root, the user's copy, which has a "Mark as read" tick) and `_Dashboard/defaults/_Help_Guide.md`. Doc changes go in both. Update README too. Screenshots live in `_Dashboard/defaults/Screenshots/` and `_Images/Screenshots/` (same names). They were last made (2026-11) by driving headless Chrome over the DevTools protocol from a throwaway node script against a seeded scratch copy, with `os.hostname` overridden so no real computer name shows. `HelpGuide.pdf` in the root is printed from the rendered help page the same way (Chrome `Page.printToPDF`: logo/title header, faint logo watermark, no sidebars or Mark as read, a small two-column contents that fits page 1, and each `##` step starting a new page). Regenerate it whenever the guide or its screenshots change. The guide's headings have no step numbers: the help page builds a numbered contents list from its `##` headings (`addContents` in `js/help.js`), and cross-references are `[Heading](#slug)` links (slug as `markdown.js` `slug()`). `md-link` only opens a new tab for links that don't start with `#`.
- Comments are short, plain English, explaining *why*. Match the existing style; the user cares about tidy, readable code.
- User-visible text uses British spelling (colour, organise).

## Server (`_Dashboard/server.js` plus `lib/`)
- `server.js` (~760 lines) is routing only: the `route()` list, `isX` validators, `handleEdit`, `isTrustedRequest`, static files, `tags.js`/`components.js`, login handlers, start-up. The work is in `lib/`, layered so each module only requires those before it (no cycles): `context` (requestContext, `at()`/`dataPaths`, entities, the per-request read cache, `disk`, `readIfExists`, `DASHBOARD_DIR`) → `renames` → `store` (option/status/tentacle readers, project listing, catalogs, `writeFileSafely`, change logs, `editableFile`, `updateProjectFile`, `NETWORKING`) → `tasks` (scopes, `collectTodos`, `changeStatus`, `checkBox`, `networkingFiles`) → `networking` → `documents` (project/tentacle/archive/incubator pages and their edits, `makeProject`, changelog and conflicts) → `compatibility` → `timeline` → `review` (review, agenda, reports, Task Archive) → `settings` (setup, Options tables, `prepareEntity`) → `nav` (menu, Dashboard, Plan, help tick). New code goes in the lowest module whose needs it fits; if it needs something higher up, move that helper down rather than requiring upwards. Never use `__dirname` in `lib/` for app paths: use `DASHBOARD_DIR`/`PUBLIC_DIR`/`ROOT_DIR`.
- Helper modules: `todos.js` (status-prefixed items, header parsing), `document-edits.js` (block/milestone/line edits), `catalogs.js`, `changes.js` (line diff, change logs, Syncthing conflict names).
- **Shared rules** (`public/js/rules.js`, UMD: `PMS.rules` in pages, `require`d by todos.js/document-edits.js): `CHECKBOX_ROW`, `PRIORITY`/`PRIORITY_TOKEN`/`RECUR_VALUE`/`anyPriority`, `isCancelled`, `SECTION_REVIEWED`/`SECTION_FLAG`, `ARCHIVE_MARKER`/`archiveMarker`, `timeframeEntries`/`splitTimeframe`/`timeframeText`, `MILESTONES_HEADING`/`MILESTONE_HEADING`, `indentOf`, `parseMilestones(md, archivedStatuses)` (markdown.js's `parseMilestones` wraps it with `PMS_ARCHIVED_STATUSES`). Every page loads it before `projects.js`. Change a rule there, never a copy.
- **Per-request reads** (`lib/context.js`): `readText(full)`, `readDir(dir)` (Dirents, a copy each call) and `existsNow(full)` are remembered for the request (`remembered`). Every disk change goes through `disk.writeFile/rename/rm/rmdir/unlink/mkdir/copyFile`, which calls `forgetReads()` before and after, so never call `fs.promises` write functions directly. `handleEdit` runs `apply` with a fresh cache. Read-before-write paths (`updateProjectFile`, `writeFileSafely`'s before-text) read the disk directly.
- Routing is a flat `if (url.pathname === …)` list in `http.createServer`. All POSTs go through `handleEdit(req, res, isValid, apply)`, which checks `isTrustedRequest` (same origin, loopback by default), requires JSON, validates the body with an `isX` predicate, then runs `apply` inside `enqueueWrite` (writes are serialised).
- `apply` returns `{ code, body }`.
- **Writing files**: `writeFileSafely(full, data)` (temp file + rename, the rename retried by `renameOver` on EPERM/EBUSY/EACCES at 50–800 ms, as Syncthing or Obsidian can hold a file on Windows) for existing files. New files use `fs.promises.writeFile(..., { flag: 'wx' })`. Markdown writes are logged to the changelog (see below), so new markdown write paths must go through `writeFileSafely` or call `recordCreated`.
- **Path safety**: documents are addressed by `{ folder, file }`, never raw paths. `editableFile(folder, file)` resolves them: a project folder name, `tentacle:<ID>`, `networking:<page>`, or `archive` (`_Archive.md`, for the Archive Index's Raw view and double-click edits; field values use the `value` kind of `api/text`). It only matches real listed entries.
- `listMarkdown(dir)` lists the `.md` files of a project or tentacle folder, skipping Syncthing conflict copies.
- **Main file**: `primaryFile(project)` / `pickPrimary` picks the file named after the folder's title (`namedFile`, case and `_`/space insensitive), else the first alphabetically. `project.files` and a tentacle's `files` are sent main-first, which is the file tab order. Compatibility flags a project with no named file (`missingMainFile`, `choose: 'main'`). Its Fix issues takes `main` (renamed to `Title.md` with its change logs by `renameToMain`) and `leader` (a leader tag for missing, empty or unknown Leader problems marked `choose: 'leader'`). A header still saying `**Owner**` (the old name, read by `findLeader` in todos.js) is the fixable "Owner should be Leader" (`fix: { renameLeader }`, `renameOldLeader`); `_Archive.md` entries with it are extra Projects rows keyed `archive:LINE` (`oldLeaderEntries`, `fixArchiveLeader`).
- **Options** (the entity's `_Options/Options.csv`, `Option,Value`): read fresh on every use via `readOptions()`. On/off options are declared in `SWITCH_OPTIONS` with defaults. The Options page lists them as tick boxes even when absent from the file, and saving adds them. Add a `TOGGLE_NOTES` entry in `public/js/options.js` for each new switch. Dropdown options go in `CHOICE_OPTIONS` (values + fallback, read with `readChoice`) with a `CHOICE_NOTES` entry: ARCHIVEMODE, THEME and CORNERS.
- **Project Dependency** (2026-11) is a list: `Name (Milestone; Milestone), Name`, parsed by rules.js `dependencyEntries` and written by `dependencyText` (re-exported by todos.js), built on the timeframe helpers; an old single name is one whole-project entry. Server: store.js `resolveDependencies` (each entry's `target` via `resolveDependency`), `dependencyChoices` (`{ id, name, milestones }`, loop check over every parent via `dependencyGraph`), `cleanDependencies(list, choices)` (unknown name or repeat refused, unknown milestones dropped, all or none = whole project). `/api/dependency`, `/api/archive-entry` and `/api/incubator` take `dependencies: [{ name, milestones }]` (`isDependencyList`). Pages get `dependencies` (project, archive entries, ideas) and show them with `PMS.dependencyLinks`; the shared picker is `PMS.dependencyPicker(form, choices, current)`/`readDependencyPicker(form)` (templates `dependency-picker`, `dependency-row`, `dependency-milestones`, `dependency-milestone`, `dependency-item` in status.html), in a `formDialog` on the project page (status.js `dependencyDialog`, opened by `.dependency-edit` before the menu code). Timeline rows carry `dependencies: [{ target, milestones }]`; timeline.js `departureBar` (named milestones' bars, else whole-project bars, else none), `arrivalBar` and `dependencyMet` (`is-met` path and `gantt-arrowhead-met`).
- **Archived projects**: `isArchived(p)` = dated folder (`ARCHIVED_FOLDER`) or any Date Closed (`project.closed`, set in `listDirectory`). Use it, never the folder regex alone. Archived projects are hidden everywhere, even with SHOWARCHIVED. The project page's Archive button (`archiveProject`) sets Date Closed, then by ARCHIVEMODE either appends the header to `_Archive.md` (HEADERS, default; folder untouched because it's moved off to a NAS) or renames the folder `YYYY-MM-DD_…` (FULL). The Timeline's `archive` rows come from `_Archive.md` (HEADERS) or archived folders (FULL), never both. Archived projects only appear (Timeline rows, the Archived filter or Archive Index) while SHOWARCHIVED is on. FULL: the projects list's Archived filter. HEADERS: no filter; the menu's Archive Index (`archive.html`, `/api/archive`, add `/api/archive-entry`, remove `/api/archive-remove` via `removeNamedEntry`). In HEADERS, archive entry titles (`TENTACLEID Title`, same shape as `projectName`) are dependency targets: `resolveDependency(value, projects, archive)` gives `archive:Title`, `dependencyChoices(..., archive)` lists them as "(archived)"; pass `dependableArchive()`. `_Archive.md` holds 8 "Demo" entries (Nov 2024 to Nov 2026) added on purpose to show the Timeline zoom. Commitments were removed (2026-11) and `Commitments.md` is no longer read.
- **Incubator page** is a document like the Archive Index: `folder: 'incubator'` (`INCUBATOR_FOLDER` in `editableFile`), Ideas/Raw/Changelog views, conflicts, and double-click edits (`block` on the heading, `value` on the dependency via `raw.line`, `body` on the notes via the `parseBlocks` body).
- **Folder button** (`folder-button` template in the summary card's `corner`, `documentView.folderButton`, one document click handler): `POST /api/open-folder` → `openFolder` resolves only listed projects (`listProjects`) or `tentacle:ID` (`tentaclePlace`), then `spawn(FILE_BROWSER, [dir], { detached })` (`explorer.exe` / `open` / `xdg-open`), not awaited, with an `error` handler.
- **Tentacle Timeline**: `/api/timeline?tentacle=ID` (`tentacleTimeline`: rows whose `projectTentacleId` is ID, or archive entries starting with it; no events or releases). tentacle.html keeps `#timeline` (with `data-tentacle`) in a hidden `#timeline-holder`; `tentacle.js` `draw()` moves it into the Overview's `[data-timeline-slot]` (`tentacle-timeline` template) and back before each redraw, then fires `resize`. timeline.js drops the line tick boxes and legend items when `data-tentacle` is set.
- **Renamed core files** (`lib/renames.js`): one `RENAMED` table (`key`, `folder`, `where: 'root'|'networking'`, `from`, `to`, `href`, `why`, `title`) drives both the old-name fallbacks and Compatibility's **Core files** page (`type=core`, `incompatibleCoreFiles`, `fixCoreFile`, `renameWithLogs` shared with `renameToMain`). `currentName(dir, key, existsNow)` gives the new name, or the old one while only that exists: `dataPaths` uses it for `_Tentacles` (was `_Entities`) and `_Options` (was `_Labels`), and `NETWORKING.contacts.file` is a getter using it for `Contacts.md` (was `Leads.md`). Folder rules' names are all in `RESERVED_DIRS`. A new rename is one row in the table. `?page=leads` and `[[Leads#...]]` (markdown.js `LINKABLE_FILES`) still open Contacts, and fixing it also renames its logs and its `#` title. The settings folder's path is `OPTIONS_DIR` (was `LABELS_DIR`).
- **Task Management tab** (Options, `data-tab="statuses"`): the `statuses` table in `label-tables.js` has `groups` (one `label-panel` per status type, titled Awaiting Assignment / Assignees / Waiting for review / Complete / Archived) and `groupBy: 'type'`; rows keep their file-wide index, each plus button carries `data-group`, and `askForRow(group)` sends that type. There's no Type column.
- **Task Archive** (`TASK_ARCHIVE_FILE`, `_Task_Archive.md` in the entity root): `submitWeeklyReview` first runs `takeArchivedRows` (document-edits.js, using `rowExtent`) on each reviewable file, then archives DONE rows in what's left (networking files re-find their entries with `sourceIn`). `taskArchiveGroups` groups by tentacle (projects by `projectTentacleName`) and `addTaskArchive` writes a newest-first `## Date archived:` section. The archive is written before the task files, inside the review's rollback. Each milestone tasks leave gets `<!-- N tasks in the Task Archive -->` (`ARCHIVE_MARKER`, `addArchiveMarker`, one per milestone, counts added together), which markdown.js `parseMilestones` counts as N done tasks; `renderLines` skips any line that is only an HTML comment. Only `GET /api/task-archive` reads it (the Options page's read-only Task Archive tab).
- **Entities tab** (Options): `label-tables.js` `entities` table → `GET/POST /api/entity-table` (`readEntityTable`, `saveEntityRow`, `editEntityCsv` in todos.js; rows keyed by Directory, the last can't be deleted). Adding a missing folder makes it and returns `created`, and the table's `afterAdd` selects the entity and opens `setup.html`; every change reloads the page. Removing leaves the folder.
- **Fix all issues** (compatibility.js `fixAll`): every box's `bodyOf` in turn, sorted by line descending so events and `archive:LINE` entries are fixed bottom-up.
- **Recurring tasks** (priority R): `PRIORITY_TOKEN` in todos.js also reads `[#R|nU]` (n 1–10, U in DWMY), giving `priority: 'R'`, `recur: { count, unit }` and `priorityLength` (tokens aren't 4 characters any more). `setPriority` takes `R|5D`; `isPriorityEdit` accepts `RECUR_VALUE`. `changePriority` schedules one period from today only when R is newly set. `POST /api/recur` → `advanceRecurring` (document-edits.js) moves SCHEDULED on with `addPeriod` (month-end clamped). Client: `data-recur` on controls; status.js sends `api/recur` instead of `change()` for a recurring status name or tick box, and choosing R opens `recurForm` (`recur-fields` template). sidebar.js `recurState` (`due` from `leadDays(recur)` before the date: 0 under 7 days' period, 1 under 28, else 7; `overdue` after it; `late` over `RECUR_LATE_DAYS` = 3 days after) puts them first with `recur-due/overdue/late` borders (caution/pending/alert). markdown.js strips the R token too.
- **Where statuses count** (2026-11): `createMatcher(statuses, scope)` takes `{ allowed(markdown) → Set of lines, strict }`; `scanLines` treats a status outside `allowed` as a plain checkbox (or skips the line when `strict`), and marks any item outside `allowed` with `outside: true`. A box with no status (untagged, or a stray tag shown as plain) is toggled by `POST /api/check` (`checkBox` → todos.js `toggleCheckbox(markdown, line, text, checked, statuses, allowed, now)`): inside `allowed` ticking moves it to DONE like before, elsewhere it only flips `[ ]`/`[x]`. Client: status.js `toggleBox` (uses `data-mark`); `outside` boxes have no status caret. Unscoped matchers (edits by line) see everything. Scopes: `taskScope()` (server, `taskBlockLines` in todos.js: checkbox rows under `###` in `## Milestones` or a TASKLISTS `##`) and `networkingScope(page)` (`entryTaskLines`: checkbox rows in an entry's Tasks field; contacts gained a Tasks field). Used by `collectTodos`, page `todos`, the Plan page (strict), `reviewableFiles` (`f.scope`), `doneItems`, `submitWeeklyReview` and `takeArchivedRows`. Compatibility: `strayStatusProblems`.
- **Section review** (2026-11): `**Date Reviewed**:`/`**Flagged for Review**: Yes` straight under a `##`–`####` heading (`sectionMeta`, `setSectionFlag`, `markSectionReviewed`, `flaggedSections` in document-edits.js; `parseBlocks`, `parseEntries` and markdown.js `parseMilestones` skip them; Incubator via `INCUBATOR_FIELDS`). `todos.js` `headerLines` limits `parseHeader`/`setHeaderField`/`setReviewFlag` to before the first `##`. Routes `section-flag`, `section-reviewed` (also sets the file's Date Reviewed for projects/tentacles); `collectFlaggedSections` feeds the Review page's `sections` box and the yellow menu count. Client: `documentView.sectionReview(doc, line, title, reviewed, flagged)` gives the flag button and date for milestone, scratch-block, entry and idea cards.
- **Timeframe milestones**: `splitTimeframe`/`timeframeText` (rules.js, re-exported by todos.js and as `PMS.splitTimeframe`); `timeframeEntries` ignores commas in brackets; `parseTimeframes` ranges carry `dates` and `milestones`; `chosenMilestones` (server) keeps real names and drops brackets when all are chosen; timeline.js colours each bar by its own milestones and `drawArrows` joins each project's bars in date order (`data-order`); `unknownTimeframeMilestones` on Compatibility.
- **Subtasks**: `deleteRow` removes the row's whole `rowExtent` (dates and subtasks). `moveToStatus` (todos.js) entering a DONE type first moves each open, uncancelled, unticked subtask under the row (`lastNestedLine`) to the same status, bottom-up, then the row, so every path (`api/status`, `api/check`, `finishMilestone`) cascades. `addMilestoneItem`/`addTask`/`addEntryTask` take `depth` (`nestedRow`); `indentRow` and `reorderRow` (document-edits.js, return `{ refused }` when they can't) behind `/api/row-indent` and `/api/row-reorder` (`shiftRow`). Client: edit.js Tab handling in `quickAdd` and `startEditing`; markdown.js `countSubtasks` and the `dragRows` render option (row handles); document-view.js handles row drag and drop within one `.milestone`/`.tasks-section`.
- **Todos jump**: `status.itemLink` adds `&line=N`; `documentView.goToLine` outlines the row (`is-target-row`), opening a collapsed milestone. Schedule/Deadline are in the row menu (`row-menu-actions`), not the status menu.
- **Contacts/Events Tasks fields** are task lists: networking.js `tasksRow` renders the `entry-tasks` template (`.entry-field.tasks-section`, so drag and Tab depth work as in task lists) with `dragRows`, per-row `todo` edits and an `entry-task` plus button (`data-line`/`data-title` of the entry) → `POST /api/entry-task` (`saveEntryTask` in lib/networking.js, `addEntryTask` in document-edits.js, which adds `**Tasks**` if missing). edit.js `blankRow` puts the quick-add row in `.entry-tasks-body`.
- **Todos from Contacts/Events**: `collectTodos` adds `networkingFiles()` items inside an entry, with `networking: { page, name, title }` (no tentacle); `status.itemLink` links them to `networking.html?page=X#Title`, and sidebar.js `projectOf` skips them.
- **`##`-entry files** (`_Archive.md`, `_Incubator.md`, in the entity's folder): `parseNamedEntries(markdown, FIELDS)`, `addNamedEntry`, `addEntryMark` in document-edits.js, and `appendNamedEntry` in server.js. ## Entities, tentacles and leaders (added 2026-11)
- `readEntities()` reads `entities.csv` in the main folder (`ENTITIES_FILE`, `Name,Directory`) on every request; it was `_Dashboard/entities.csv` until 0.8, and start-up's `moveOldEntitiesFile` moves it up (`OLD_ENTITIES_FILE`), never over a new one; no usable rows means one entity at the main folder (`FALLBACK_ENTITY`). The `pms_entity` cookie picks one (`selectedEntity`, set by `POST /api/entity-select`, which also runs `prepareEntity`).
- `http.createServer` runs `route()` inside `requestContext.run({ root, entity })`; `handleEdit` adds `user` to that store. **Every data path is `at().X`** (`dataPaths(currentRoot())`: `TENTACLE_DIR` (the `_Tentacles` folder), `OPTIONS_DIR` (the `_Options` folder), `TENTACLES_FILE`, `OPTIONS_FILE`, `ARCHIVE_FILE`, …), never a module constant, so new code must use `at()` too. `ROOT_DIR`, `HELP_FILE`, `IMAGES_DIR` stay constant. Start-up runs `prepareEntity` for each entity.
- The entity dropdown is `PMS.entityPicker()` in `js/projects.js` (menu, setup and login pages). Per-entity browser storage (Plan picks, sidebar filters, milestone collapse) is keyed by `PMS_ENTITY`.
- Naming: in code and UI, a row of Tentacles.csv is a **tentacle** (`readTentacles`, `tentaclePlace`, `TENTACLE_PREFIX`, `tentacle.html`, `/api/tentacle`, `/api/tentacle-tag` for a page title's tentacle keyword) and the person is a **leader** (`**Leader**` header, `LEADER_FIELD`). The header/leader/type buttons share the `header-control`/`header-button` classes.

## Multi-user and Syncthing (added 2026-11)
- NAS read/write modes were considered and **rejected**: Syncthing handles sharing files between machines. Don't reintroduce network-path options.
- `SYNCCONFLICTS` switch: scans the open document's folder for `Name.sync-conflict-YYYYMMDD-HHMMSS-DEVICE.md`. It shows a diff with **Keep current** (deletes the copy) or **Use this version** (writes it over the file, then deletes the copy). API: `GET /api/conflicts`, `POST /api/conflict`.
- `MULTIUSER` switch: login picks a leader from `Leaders.csv`, stored in the `pms_user` cookie. The device is always the server's `os.hostname()`, never user-chosen, so the number of logs stays stable. Every markdown write appends to `<name>-change.<HOSTNAME>.log` next to the file. There is **one log per device** so Syncthing never sees two writers on one log. Entries older than 2 × `ROUNDUP` days are pruned on write. The Changelog view merges every device's log for the file (`GET /api/changelog`).
- User identity reaches the write helpers through `AsyncLocalStorage` (`requestContext`), set in `handleEdit`.
- Trust model: collaborative equals, so no passwords or encryption. The login is identification, not security.
