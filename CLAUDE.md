# Octapu System: notes for Claude

A markdown-based project management system (PMS) for an organisation made of entities (orgs/labels) and their "tentacles" (sub-entities). Data are plain markdown and CSV files that the user also edits by hand (e.g. in Obsidian) and shares between machines with Syncthing. `_Dashboard/` is a local web app that reads and edits those files.

The README is the user-facing reference. Its sections on file layout, code organisation, options and markdown formats are accurate, so read the relevant section before changing behaviour. `_Help_Guide.md` is the step-by-step guide shown in the app.

## Running
- `node _Dashboard/server.js` → http://127.0.0.1:4173 (`PMS_PORT`, `PMS_HOST` env vars). No `npm install`; there is no package.json.
- There's no test suite. Verify by running the server and exercising the page or API (curl the `/api/*` routes; POSTs need `Content-Type: application/json` and a matching `Origin`).
- The repo *is* the user's live data. Test against a copy (e.g. `tar` the folder, minus `.git`, into the scratchpad and run there on another `PMS_PORT`), so edits, change logs and conflict files don't land in real files.
- Developed on Windows (Git Bash + PowerShell). Python isn't assumed; use node for scripts.

## Hard rules / conventions
- **Zero dependencies.** Node built-ins only on the server, plain browser JS (IIFE per file, `'use strict'`) on the client. No build step, no frameworks, no CDN.
- **Data folders vs app**: `_Entities/`, `Projects/` (and any other dir named in `PROJECTS`), `_Networking/`, `_Time_Management/`, `_Catalogs/`, `_Labels/`, `_Images/`, `_Help_Guide.md`, `_Incubator.md`, `_Archive.md` are user data. `_Dashboard/` is the app. `_Dashboard/defaults/` holds the shipped Help Guide, screenshots, logo and colours, which are copied in only if missing.
- **Help Guide is duplicated**: `_Help_Guide.md` (root, the user's copy, which has a "Mark as read" tick) and `_Dashboard/defaults/_Help_Guide.md`. Doc changes go in both. Update README too. Screenshots live in `_Dashboard/defaults/Screenshots/` and `_Images/Screenshots/` (same names). They were last made (2026-11) by driving headless Chrome over the DevTools protocol from a throwaway node script against a seeded scratch copy, with `os.hostname` overridden so no real computer name shows. `HelpGuide.pdf` in the root is printed from the rendered help page the same way (Chrome `Page.printToPDF`: logo/title header, faint logo watermark, no sidebars or Mark as read). Regenerate it whenever the guide or its screenshots change. The guide's headings have no step numbers: the help page builds a numbered contents list from its `##` headings (`addContents` in `js/help.js`), and cross-references are `[Heading](#slug)` links (slug as `markdown.js` `slug()`). `md-link` only opens a new tab for links that don't start with `#`.
- Comments are short, plain English, explaining *why*. Match the existing style; the user cares about tidy, readable code.
- User-visible text uses British spelling (colour, organise).

## Server (`_Dashboard/server.js`, ~2.4k lines, one file plus helpers)
- Helper modules: `todos.js` (status-prefixed items, header parsing), `document-edits.js` (block/milestone/line edits), `catalogs.js`, `changes.js` (line diff, change logs, Syncthing conflict names).
- Routing is a flat `if (url.pathname === …)` list in `http.createServer`. All POSTs go through `handleEdit(req, res, isValid, apply)`, which checks `isTrustedRequest` (same origin, loopback by default), requires JSON, validates the body with an `isX` predicate, then runs `apply` inside `enqueueWrite` (writes are serialised).
- `apply` returns `{ code, body }`.
- **Writing files**: `writeFileSafely(full, data)` (temp file + rename) for existing files. New files use `fs.promises.writeFile(..., { flag: 'wx' })`. Markdown writes are logged to the changelog (see below), so new markdown write paths must go through `writeFileSafely` or call `recordCreated`.
- **Path safety**: documents are addressed by `{ folder, file }`, never raw paths. `editableFile(folder, file)` resolves them: a project folder name, `entity:<ID>`, or `networking:<page>`. It only matches real listed entries.
- `listMarkdown(dir)` lists the `.md` files of a project or entity folder, skipping Syncthing conflict copies.
- **Main file**: `primaryFile(project)` / `pickPrimary` picks the file named after the folder's title (`namedFile`, case and `_`/space insensitive), else the first alphabetically. `project.files` and an entity's `files` are sent main-first, which is the file tab order. Compatibility flags a project with no named file (`missingMainFile`, `choose: 'main'`). Its Fix issues takes `main` (renamed to `Title.md` with its change logs by `renameToMain`) and `owner` (a leader tag for missing, empty or unknown Owner problems marked `choose: 'owner'`).
- **Options** (`_Labels/Options.csv`, `Option,Value`): read fresh on every use via `readOptions()`. On/off options are declared in `SWITCH_OPTIONS` with defaults. The Options page lists them as tick boxes even when absent from the file, and saving adds them. Add a `TOGGLE_NOTES` entry in `public/js/options.js` for each new switch. Dropdown options go in `CHOICE_OPTIONS` (values + fallback, read with `readChoice`) with a `CHOICE_NOTES` entry; ARCHIVEMODE is the only one.
- **Archived projects**: `isArchived(p)` = dated folder (`ARCHIVED_FOLDER`) or any Date Closed (`project.closed`, set in `listDirectory`). Use it, never the folder regex alone. Archived projects are hidden everywhere, even with SHOWARCHIVED. The project page's Archive button (`archiveProject`) sets Date Closed, then by ARCHIVEMODE either appends the header to `_Archive.md` (HEADERS, default; folder untouched because it's moved off to a NAS) or renames the folder `YYYY-MM-DD_…` (FULL). The Timeline's `archive` rows come from `_Archive.md` (HEADERS) or archived folders (FULL), never both. Archived projects only appear (Timeline rows, the Archived filter or Archive Index) while SHOWARCHIVED is on. FULL: the projects list's Archived filter. HEADERS: no filter; the menu's Archive Index (`archive.html`, `/api/archive`, add `/api/archive-entry`, remove `/api/archive-remove` via `removeNamedEntry`). In HEADERS, archive entry titles (`OWNERID Title`, same shape as `projectName`) are dependency targets: `resolveDependency(value, projects, archive)` gives `archive:Title`, `dependencyChoices(..., archive)` lists them as "(archived)"; pass `dependableArchive()`. `_Archive.md` holds 8 "Demo" entries (Nov 2024 to Nov 2026) added on purpose to show the Timeline zoom. Commitments were removed (2026-11) and `Commitments.md` is no longer read.
- **`##`-entry files** (`_Archive.md`, `_Incubator.md`, in the main folder): `parseNamedEntries(markdown, FIELDS)`, `addNamedEntry`, `addEntryMark` in document-edits.js, and `appendNamedEntry` in server.js. Incubator ideas are `## OWNERID Title`, and are hidden once they have `**Archived**:` or `**Promoted**:`. Promote uses `makeProject` (shared with New project).
- **Events** (`NETWORKING.events`): fields with a `kind` (`date`, `range`, `yesno`) have their own controls and are written on one line by `setInlineField` via `POST /api/event-field`. Dates are stored `YYYY-MM-DD` or `YYYY-MM-DD to YYYY-MM-DD` (`parseEventDate`). Hand-written dates are read by `readOldEventDate` and converted on Compatibility > Events (`incompatibleEvents`/`fixEvent`, keyed by heading line + title). Events list as Upcoming/Past by date, ignoring the file's headings. `eventProgress(entry)` gives open/applied/booked (from the Yes/No fields): it drives the card borders and the Events page filters (`?filter=`, since `#` is used for entry links), and on the Timeline only open events get a deadline line and only booked ones are purple (others grey).
- Other label CSVs: `Status.csv`, `Owners.csv` (entities, `id,Name,Parent`), `Leaders.csv` (people, `Tag,Name`), `Colours.csv` (theme).
- `/api/owner-tags.js` is a script every page loads that sets `window.PMS_*` globals (owner IDs, archived statuses, SHOWARCHIVED, MULTIUSER, SYNCCONFLICTS, ARCHIVEMODE, the logged-in user). Use it for small per-page flags.
- `serveStatic` redirects every `.html` to `setup.html` while first-time setup is needed. When MULTIUSER is on, it redirects to `login.html` if no one is logged in.

## Client (`_Dashboard/public/`)
- Every page loads `api/components.js`, `js/projects.js` (shared helpers on `window.PMS`: `component`, `getJson`, `postJson`, `readJson`, `escapeHtml`, `setViewInAddress`, …), `api/owner-tags.js`, then page scripts.
- **HTML only in templates**: `public/components/*.html` `<template name="…">`. Use `{{x}}` for escaped values, `{{{x}}}` for raw HTML and `{{#if x}}…{{else}}…{{/if}}` for optional markup. Newlines and indentation are stripped. Render with `PMS.component(name, data)`.
- Document pages (`project.html`, `entity.html`, `networking.html`) share `js/document-view.js`. Each has a `[data-view]` toggle (Overview/List, Scratchpad, Raw, Changelog) and a `draw()` that renders the current view into `#content`. The loaded doc object carries `folder` and `file`.
- `js/changes.js` (`PMS.changes`) provides the Syncthing conflict warning (`#conflicts` above `#content`) and the Changelog view for those pages.
- `js/timeline.js`: zoom (3/6/12 months, `pms.timeline.zoom`) sets `--gantt-month` from the scroller width; `showNearbyRows` hides rows with no bar within 2 months of the months on screen, on scroll, and arrows only join visible rows.
- `js/nav.js` is the left menu, which shows the logged-in user and Log out when MULTIUSER is on. `js/status.js` holds the status controls plus `status.refresh()` / `status.onChange()` for reloading after edits.
- Styling: `public/css/style.css`, using CSS variables (`--green`, `--pink`, `--orange`, `--yellow`, `--accent`, `--surface`, `--border`, `--text-soft`, …). A global `[hidden] { display: none !important }` means the hidden attribute always wins over a rule that sets display.
- Generate report (`js/dashboard.js`) clones the Overview; it fires `pms:report-start`/`pms:report-end` so the Timeline shows every row (and redraws arrows) for the copy.

## Multi-user and Syncthing (added 2026-11)
- NAS read/write modes were considered and **rejected**: Syncthing handles sharing files between machines. Don't reintroduce network-path options.
- `SYNCCONFLICTS` switch: scans the open document's folder for `Name.sync-conflict-YYYYMMDD-HHMMSS-DEVICE.md`. It shows a diff with **Keep current** (deletes the copy) or **Use this version** (writes it over the file, then deletes the copy). API: `GET /api/conflicts`, `POST /api/conflict`.
- `MULTIUSER` switch: login picks a leader from `Leaders.csv`, stored in the `pms_user` cookie. The device is always the server's `os.hostname()`, never user-chosen, so the number of logs stays stable. Every markdown write appends to `<name>-change.<HOSTNAME>.log` next to the file. There is **one log per device** so Syncthing never sees two writers on one log. Entries older than 2 × `ROUNDUP` days are pruned on write. The Changelog view merges every device's log for the file (`GET /api/changelog`).
- User identity reaches the write helpers through `AsyncLocalStorage` (`requestContext`), set in `handleEdit`.
- Trust model: collaborative equals, so no passwords or encryption. The login is identification, not security.
